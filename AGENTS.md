# AGENTS.md --- Triply

## Project Overview

Triply is a mobile-first collaborative group-trip expense tracker.

A tour organizer creates a tour and shares an invitation link with
friends. Members join the tour using their own accounts, record shared
expenses, see who paid and who participated, track personal/group
balances, and settle money at the end of the trip.

The application should work reliably during travel, including poor or
intermittent connectivity.

## Product Goal

Build a simple, polished, premium-feeling expense-sharing experience for
small travel groups.

The core loop is:

1.  Create or join a tour.
2.  Invite/join members.
3.  Record an expense quickly.
4.  Select who paid.
5.  Select who participated.
6.  Split equally.
7.  Recalculate balances.
8.  Record settlements.
9.  Keep data usable during weak/no connectivity.

Do not turn Triply into a general accounting, ERP, itinerary, or social
networking product.

## Current Product Direction

-   Mobile-first web application / PWA.
-   React code generated by Figma Make is the visual implementation
    baseline.
-   Figma design is the visual source of truth.
-   The application will be used collaboratively by multiple people in
    the same tour.
-   Each interactive participant should normally have an authenticated
    account.
-   A tour may also contain Guest members who participate financially
    without an account.
-   A Guest can later link/claim their existing membership after
    creating an account.
-   The tour creator automatically becomes an Owner and a member.
-   Tours use reusable invitation links for joining.

## Development Principles

### 1. Preserve the approved UI

The existing Figma Make implementation is the visual source of truth.

When implementing functionality:

-   preserve layouts;
-   preserve typography;
-   preserve spacing;
-   preserve component hierarchy where practical;
-   preserve responsive behavior;
-   preserve visual states;
-   reuse existing components.

Do not redesign, simplify, restyle, or replace an approved component
merely because another implementation is easier.

If a technical requirement genuinely requires a visual change, make the
smallest possible change and document the reason.

### 2. Do not rewrite the generated application

Refactor incrementally.

Before changing architecture:

1.  inspect the existing implementation;
2.  understand the component/data flow;
3.  identify duplication or hardcoded data;
4.  make the smallest safe change;
5.  verify that existing screens still render correctly.

Avoid large speculative refactors.

### 3. Separate presentation from business logic

UI components must not become the source of truth for financial
calculations.

Prefer:

`UI -> feature/service layer -> local data layer -> sync/backend`

Financial calculations should live in reusable pure functions/services
and be consumed consistently by Home, Expenses, Members, and Settlement.

### 4. Replace mock data gradually

Figma Make mock data should be replaced with real application data
without rebuilding the visual layer.

Do not leave duplicate sources of truth such as:

-   hardcoded expenses plus database expenses;
-   local member arrays plus Supabase members;
-   screen-specific balance calculations.

## Membership Rules

There are three important membership states.

### Owner

-   authenticated;
-   created the tour;
-   automatically becomes a tour member;
-   can manage the tour;
-   can invite/add members;
-   can add expenses;
-   can manage expenses when necessary;
-   can complete the tour.

### Member

-   authenticated;
-   linked to a `tour_members` record;
-   can view the tour;
-   can add expenses;
-   can view group expenses and balances;
-   can edit/delete expenses they created;
-   can participate in settlements.

### Guest

-   has a `tour_members` record;
-   has no linked authenticated account;
-   participates fully in financial calculations;
-   may be payer;
-   may be an expense participant;
-   may owe/receive money;
-   may participate in settlements;
-   cannot independently access the application.

Guest is a normal financial state, not an error state.

If a Guest later creates an account and identifies themselves, link
their account to the existing membership.

Do not create a duplicate member.

Preserve all existing expenses, shares, balances, and settlements.

## Invitation Flow

Primary collaborative onboarding:

`Create Tour -> Share Invite Link -> Friend Opens Link -> Sign Up/Sign In -> Join Tour -> Home`

Requirements:

-   preserve invitation context through authentication;
-   do not send an invited user to the generic Tour List after
    authentication;
-   require explicit Join confirmation;
-   if already a member, open the tour;
-   if appropriate Guest memberships exist, allow the user to identify
    an existing Guest using human-friendly language such as "This is
    me";
-   prevent multiple accounts from linking to the same membership;
-   allow the owner to reset/revoke an invitation link;
-   do not expose tour financial data before membership is established.

For MVP, one reusable invitation link per tour is sufficient.

Do not build individual email/SMS invitations unless explicitly
requested.

## Expense Rules

An expense must have:

-   tour;
-   amount greater than zero;
-   description;
-   category;
-   payer;
-   expense date;
-   at least one participant.

### Payer and participants are independent

Never force the payer to participate in the split.

Example:

Rafi pays ৳1,000.

Participants:

-   Nadia
-   Tanha

Result:

-   Rafi paid: ৳1,000
-   Rafi share: ৳0
-   Nadia share: ৳500
-   Tanha share: ৳500

### Split method

MVP supports equal split among selected participants only.

Do not implement:

-   percentage split;
-   weighted shares;
-   custom amounts;
-   multiple payers;

unless explicitly added to scope.

### Money

Never use floating-point arithmetic directly for persisted monetary
calculations.

Use integer minor units or another precise monetary representation.

Formatting belongs in presentation utilities.

The default product currency is BDT / ৳, while the tour model may retain
a currency field for future flexibility.

------------------------------------------------------------------------

## Balance Rules

Before settlements:

`balance = totalPaid - totalShare`

Interpretation:

-   positive -\> member should receive money;
-   negative -\> member owes money;
-   zero -\> settled.

After settlements:

`balance = totalPaid - totalShare + settlementsPaid - settlementsReceived`

A debtor paying a settlement moves their balance toward zero.

A creditor receiving a settlement moves their balance toward zero.

All member balances for a tour should sum to zero, apart from explicitly
handled rounding.

### Critical rule

Settlements are NOT expenses.

Recording a settlement must never increase or decrease:

-   Total Spent;
-   expense-category totals;
-   budget consumption.

------------------------------------------------------------------------

## Personalized Metrics

For an authenticated member:

`Your Share` is the sum of that member's expense shares.

It is NOT:

`Total Spent / total number of members`

because participation can differ by expense.

`Your Balance` must use the shared balance engine, not a screen-specific
calculation.

## Permissions and Security

The application is collaborative. Frontend filtering is not security.

Use Supabase Row Level Security.

At minimum:

-   users may only access tours they belong to;
-   users may only create data inside tours they belong to;
-   members may edit/delete their own expenses;
-   owners may manage their tours and perform permitted administrative
    actions;
-   users must not be able to claim an already-linked membership;
-   invitation joining must be validated server-side/database-side where
    appropriate.

Never expose Supabase service-role credentials in frontend code.

Use environment variables correctly.

Do not disable RLS as a shortcut.

## Offline-First / PWA Requirements

Triply is used while travelling, so poor connectivity is expected.

The UI should not block routine expense entry merely because Supabase is
temporarily unavailable.

Target flow:

`User action -> save locally -> update UI optimistically -> sync when possible`

Use IndexedDB/Dexie for appropriate local data.

Cache enough previously loaded tour data to keep the active tour useful
offline, including where practical:

-   active tour;
-   members;
-   categories;
-   recent expenses;
-   calculated balances.

### Sync states

Support clear states such as:

-   synced;
-   saving;
-   offline;
-   pending sync;
-   sync failed.

Normal synced state should generally require no persistent status UI.

Pending-online status should remain subtle.

Offline and sync-failure states may receive stronger status treatment.

### Duplicate protection

Offline-created records require stable client-generated
identifiers/idempotency protection so retries cannot create duplicate
expenses.

Do not rely only on `navigator.onLine` to determine whether a server
operation succeeded.

### Sync queue

Keep sync behavior deterministic.

Where practical, collapse unnecessary queued operations when an
offline-created record is edited or deleted before it ever syncs.

Do not blindly cache Supabase/API responses through the service worker.

## App Shell Rules

The tour-level shell contains:

-   contextual top app bar;
-   page content;
-   global Add Expense action where appropriate;
-   bottom navigation.

Primary bottom-navigation destinations:

-   Home
-   Expenses
-   Members
-   Settle

Add Expense is an action, not a fifth navigation destination.

Tour List and authentication exist outside the tour-level
bottom-navigation shell.

### Safe areas

All mobile layouts must respect device safe areas.

No application content may collide with:

-   Dynamic Island;
-   camera cutouts;
-   notches;
-   home indicator/system gesture areas.

Use adaptive safe-area handling rather than hardcoded offsets for a
specific phone mockup.

For PWA/web implementation, use appropriate viewport configuration and
CSS safe-area environment variables.

## Design Quality

Triply should feel:

-   premium;
-   calm;
-   confident;
-   modern;
-   warm;
-   travel-friendly;
-   financially trustworthy.

Premium does not mean decorative.

Avoid:

-   excessive gradients;
-   glassmorphism;
-   heavy shadows;
-   neon;
-   excessive card nesting;
-   unnecessary animations;
-   generic SaaS dashboard styling.

Preserve the established visual hierarchy, surface system, typography,
spacing, and restrained ocean-teal brand direction.

## Accessibility

Do not sacrifice accessibility to match a mockup.

Minimum expectations:

-   semantic buttons/links/inputs;
-   visible labels;
-   keyboard accessibility;
-   useful focus states;
-   sufficient contrast;
-   approximately 44px touch targets for primary mobile controls;
-   accessible bottom sheets/dialogs;
-   meaningful error messaging;
-   reduced-motion consideration;
-   no information conveyed only through color.

------------------------------------------------------------------------

## Responsive Behavior

Mobile is the source of truth.

The app must still adapt intentionally to larger widths.

Do not simply stretch a 390px mobile layout across desktop.

Likewise, do not permanently render the application as a narrow phone
floating in the center of a desktop browser.

Desktop/tablet adaptations should preserve the same product architecture
and design language.

## Code Quality Rules

-   TypeScript should remain strict where practical.
-   Avoid `any` unless there is a documented reason.
-   Prefer small focused components.
-   Extract reusable logic only when reuse/complexity justifies it.
-   Avoid premature abstraction.
-   Do not introduce a global state library unless existing React
    patterns become insufficient.
-   Keep network/database operations out of purely presentational
    components.
-   Centralize financial calculations.
-   Centralize currency/date formatting.
-   Validate inputs at appropriate boundaries.
-   Handle loading, empty, error, offline, and permission states
    explicitly.
-   Remove dead mock code once real functionality replaces it.
-   Do not leave commented-out generated alternatives.
-   Avoid adding dependencies for trivial functionality.

3.  state the smallest implementation plan;

5.  run available validation/tests;
